# Общий API-контракт RedOrda

React → `/api/v1/` → Django 5.2 → Celery → общий `campaign_engine` → публичная среда Beeline.
Источник машинных схем: [openapi.yaml](openapi.yaml); подробные ответы: [backend-api.md](backend-api.md).

Контракт задач и команд: [team-contract.md](team-contract.md). Интегрированы
хранение задач/артефактов, неизменяемые snapshot, HTTP API и очередь команд Celery.
`create_plan` создаёт связанный черновик с новым бюджетом. `explain`/`compare`
ожидают реализации функций анализа snapshot в AI-движке и пока отсутствуют в
`available_commands`; прямой запрос завершается `failed/capability_unavailable`.
Ограничение `allowed_channels` для нового плана пока также требует поддержки движка.

## Доступ и договорённость для frontend

При `DJANGO_DEBUG=0` API всегда требует активного пользователя, независимо от
`REDORDA_REQUIRE_AUTH`. В локальной разработке включить это поведение можно через
`REDORDA_REQUIRE_AUTH=1`. Пользователи работают в общей командной рабочей области;
разделения планов по владельцам пока нет. Пользователь создаётся администратором
через `manage.py createsuperuser`; публичной регистрации и встроенных паролей нет.

Frontend использует один origin, `credentials: 'same-origin'` и следующий порядок:

1. `GET auth/me/` → `{authenticated: false, user: null}` либо данные текущего пользователя.
2. `GET auth/csrf/` → `{csrf_token: string}`; ответ также устанавливает cookie `csrftoken`.
3. `POST auth/login/` с JSON `{username, password}` и заголовком `X-CSRFToken`.
   Ответ 200: `{authenticated: true, user: {id, username, is_staff}, csrf_token}`.
   После входа токен меняется — дальнейшие запросы используют **токен из ответа login**.
4. `POST auth/logout/` с действующим токеном → 200, анонимная сессия и новый токен.

`sessionid` — HttpOnly cookie; в production обе cookie Secure, SameSite=Lax.
Для всех POST нужен `X-CSRFToken`. Неверный пароль/неактивный пользователь: 401
`invalid_credentials`; отсутствие сессии: 403 `not_authenticated`; ошибка CSRF:
403 `csrf_failed` на login/logout либо `permission_denied` на остальных POST.
Ограничение login: 10 попыток/минуту на IP, затем 429 `throttled`.
При `not_authenticated` frontend останавливает polling и показывает вход; CSRF обновляется через
`auth/csrf/`. Пароль и session cookie не сохраняются в localStorage.

`health/`, `ready/`, auth discovery, `/api/schema/` и `/api/docs/` доступны без входа.
Данные и операции API требуют сессии в публичном режиме. Frontend реализует этот
порядок в `src/api/client.ts`: сначала проверяет сессию, получает CSRF перед POST,
после входа использует новый токен. Интерфейс показывает форму входа до загрузки данных. Ключ OpenAI передаётся только серверу через
окружение; поля для него в браузере нет.

## Маршруты

| Метод | Путь относительно `/api/v1/` | Результат |
| --- | --- | --- |
| GET | `health/` | Доступность Django и БД |
| GET | `ready/` | 200: `{status: "ok", database: true, broker: true}`; 503 при сбое БД/Redis |
| GET | `meta/` | Лимиты, стоимость каналов, флаги функций, `environment: {mode, label}` |
| GET | `datasets/current/` | Импортированная сводка; 404 при отсутствии |
| POST | `datasets/import-demo/` | Импорт четырёх встроенных CSV; 201 новый / 200 повторный |
| POST | `datasets/import/` | Загрузка четырёх CSV через multipart `files`; 201 новый / 200 повторный |
| GET / POST | `runs/` | История / сохранение черновика; без датасета 409 `dataset_required` |
| GET | `runs/{id}/` | Состояние и параметры плана |
| POST | `runs/{id}/start/` | 202; обязателен `Idempotency-Key` длиной 1–255 |
| POST | `runs/{id}/cancel/` | 200; draft → 409; queued отменяется сразу, running — между шагами |
| GET | `runs/{id}/events/?after=0&limit=100` | `{results, next_after, has_more}`, limit 1–200 |
| GET | `runs/{id}/results/` | Сохранённые кампании, totals, warnings; до completed — 409 |
| GET | `runs/{id}/export/` | Стабильный UTF-8 CSV из БД; до completed — 409 |
| GET | `runs/{id}/team/` | Snapshot команды: задачи, артефакты, доступные команды и `last_event_id` |
| POST | `runs/{id}/commands/` | 202; команда `explain`, `compare` или `create_plan`; обязателен `Idempotency-Key` |
| GET | `runs/{id}/commands/{command_id}/` | Сохранённый статус и результат команды; чужой run — 404 |

Команды используют тот же Django session/CSRF, что и `start/`. Клиент сначала
получает `team/`, затем запрашивает события с `after=last_event_id`. `snapshot_id`
передаётся в POST без изменения. Параметры и примеры приведены в
[backend-api.md](backend-api.md). `pause`, `resume` и дополнительный ручной пилот
не поддерживаются и не появляются в `available_commands`.

POST `runs/`: `name`, `budget` (decimal-строка), `max_contacts`, `max_pilots`, `seed`,
`strategy="baseline" | "openai"` (по умолчанию `baseline`). Датасет выбирает сервер.
Создание `openai` при выключенном `meta.features.openai_strategy` возвращает
400 `validation_error` с полем `strategy`. Неизвестные поля запрещены.
Списки планов: `{count, next, previous, results}`. Ошибки: `{error: {code, message, fields}}`.
ID — UUID; время — ISO 8601; бюджет и итоговые расходы — decimal-строки.
Прогнозы и числовые поля публичных наблюдений остаются JSON numbers. События имеют возрастающий
числовой ID; клиент сохраняет `next_after` даже после пустой страницы.

## Импорт из интерфейса

`POST datasets/import-demo/` принимает пустое тело или `{}` и использует файлы
из `data/demo/`. `POST datasets/import/` принимает `multipart/form-data` с четырьмя
повторениями поля `files`: `dict_tariff.csv`, `traffic.csv`, `arpu_monthly.csv`,
`change_tariff.csv`. Имена должны совпадать точно. Кодировка UTF-8 (BOM допустим),
разделитель — запятая, заголовки и столбцы — как в демонаборе. Максимум 30 МиБ
на файл и 50 МиБ на весь набор. Неизвестные поля, лишние, повторные, пустые и
недостающие файлы отклоняются. Сервер проверяет структуру строк, числовые значения
и ссылки на тарифы до смены текущего набора.

Оба метода возвращают объект `Dataset`, как `datasets/current/`. Повтор тех же
байтов использует существующий набор и делает его текущим; исходная отметка
происхождения сохраняется. Старые планы продолжают ссылаться на свои наборы.
Неудачный импорт не заменяет текущий набор. Загрузка сохраняется в закрытом
серверном хранилище `MEDIA_ROOT/datasets/`; путь не входит в ответ API.

У четырёхфайлового набора `summary.format="raw_csv"`, `source_kind="demo"|"upload"`,
`file_rows` содержит число строк по именам файлов, `tariff_count` — размер
справочника. `customer_count` — уникальные `ID_NUMBER` в `traffic.csv`.
`baseline_arpu=null`, три словаря `segments` пусты: готового прогноза и сегментов
в этих таблицах нет. `synthetic=true` для встроенного демо, `null` для загрузки
неизвестного происхождения. Семифайловый CLI-импорт сохраняет прежний формат сводки.

Фронтенд передаёт CSRF-токен в обоих POST. Прогресс передачи файлов берётся из
XHR; проверка CSV на сервере отображается отдельным состоянием без процента.
Переход между разделами приложения не отменяет начатый импорт: успешный ответ
обновляет общую сводку, даже если страница загрузки уже закрыта. Клиент ограничивает
ожидание пятью минутами; сетевой сбой сам по себе не означает отмену на сервере.
Импорт синхронный и не требует Celery. Полный пакет и реализация адаптера остаются
необходимыми для запуска симулятора; импорт четырёх CSV их не заменяет.
Ответ плана содержит `execution_blocker: string | null`: для такого набора в режиме
локального симулятора указано отсутствие профиля. Frontend отключает запуск и
показывает объяснение; сервер возвращает `503 engine_unavailable`, сохраняя черновик
без событий и задач. Идемпотентный повтор уже принятого запуска продолжает работать.

## Запуск и результат

`draft → queued → running → completed / failed / cancelled`.
Каждый ответ `Run` (создание, список, detail, start, cancel) содержит
`progress: {stage, percent, spent_budget, used_contacts, completed_pilots}`,
`error: {code, message} | null` и `cancellation_requested: boolean`.
`stage` совпадает с текущим статусом, кроме `running` с уже сохранёнными
кампаниями: тогда он равен `finalizing`. `spent_budget` и `used_contacts`
включают сохранённые пилоты и известные показатели кампаний. Если стоимость
или контакты хотя бы одной сохранённой кампании неизвестны, соответствующее
поле равно `null`; до результатов это накопленные пилоты.
`percent` равен 0 до старта, 100 только после `completed`; во время работы это
оценка по числу пилотов относительно `max_pilots`, потому что агент может
закончить раньше лимита. При сбое и отмене сохраняется достигнутая оценка.
Подтверждение отмены у `running` выставляет `cancellation_requested=true`, но
статус остаётся `running` до остановки worker. Для `queued` отмена действует
сразу, так как расчёт ещё не начался.
Тот же Idempotency-Key возвращает сохранённый запуск, включая терминальный статус,
без новой задачи и пилотов, даже если запуск новых расчётов затем отключили.
Другой ключ после старта: 409 `run_conflict`.
Блокировки строк проверены конкурентно на PostgreSQL. После сбоя публикации:
503 `execution_unavailable`, запуск становится failed с событием `queue_unavailable`.
Секреты, traceback и пути среды не входят в публичные ответы.

В коде подключён общий `run_campaigns`: backend передаёт параметры сохранённого
плана, историю выбранного dataset, observer и проверку отмены. `Agent.act` использует
тот же движок. Готовый factory —
`apps.campaigns.services.participant_environment.create_environment`; он создаёт
новую среду через публичный `make_mock_env(seed)` из полного пакета в
`Dataset.source_dir`. Стратегия получает только публичную среду.

Флаги `meta.features` отражают конфигурацию сервера:

- `run_execution=true`, когда `REDORDA_RUN_EXECUTION_ENABLED=1` и задан
  `REDORDA_ENVIRONMENT_FACTORY`.
- `openai_strategy=true`, когда дополнительно задан непустой серверный
  `OPENAI_API_KEY`. Это не проверка действительности ключа или доступа к модели.
- `csv_export=true` обозначает реализацию экспорта сохранённого результата.

При отключённых расчётах новый baseline-запуск возвращает 503 `engine_unavailable`;
недоступный OpenAI-запуск — 503 `openai_unavailable`. Черновик сохраняет `draft`,
задача не публикуется. Повтор уже начатого запуска с прежним ключом возвращает
сохранённое состояние даже после отключения функции. Флаги не проверяют наличие
worker, комплектность данных или доступность внешнего API; проверки развёртывания
описаны в [deployment.md](deployment.md). Реализация в репозитории не означает,
что текущий сервер уже обновлён и включён.

Worker не повторяет расчёт автоматически; используется prefork, soft limit 570 с,
hard limit 600 с и guard через 610 с после постановки в очередь. При потере всех
worker guard выполнится после восстановления worker; API не обещает мгновенной
фиксации сбоя при полной остановке инфраструктуры.

Перед каждым пилотом backend проверяет размер запроса 10–200, число пилотов и
достижимый охват с учётом фильтров, остатков публичной среды и стоимости канала.
Этот охват должен укладываться в лимиты плана. Ответ среды должен содержать
совпадающие фактические `cost`, `n_customers`; малая аудитория может дать меньше
запрошенного числа контактов.
Перед completed повторно проверяются сохранённые кампании и все известные расходы.
AI-разработчик отвечает за соблюдение лимитов публичной среды, выборку аудитории
финальных кампаний и проверку общих расходов при неизвестных backend метриках.

Результат: `{run_id, status, campaigns: [{rank, parameters, explanation, metrics}],
totals, warnings}`. Неизвестные расходы/контакты/эффекты — `null` с предупреждением;
прогноз и результат симуляции хранятся отдельно, эффект пересекающихся кампаний
не суммируется. Экспорт читает сохранённые результаты и не запускает стратегию
повторно. Подробнее: [backend-results.md](backend-results.md).
`parameters` содержит фильтры аудитории, `target_tariff` и `channel`;
`metrics.cost` и `metrics.n_contacts` присутствуют всегда, при отсутствии данных
равны `null`. Общий движок также сохраняет `metrics.estimated_incremental_net`.
Пустое объяснение возвращается как `null`.

Текущий `totals.predicted_effect` — объект с полями
`source="posterior_forecast_not_official_score"`, `net_arpu_gain_mean`,
`lower_tail_mean_10`, `objective`. Числовые поля прогноза — JSON numbers.
`totals.simulator_result=null`: веб-расчёт пока не выполняет отдельную оценку
итогового портфеля симулятором. Frontend подписывает эти два показателя отдельно.

## События и интерфейс

`pilot_completed` создаётся один раз после сохранения ответа среды. В payload
есть `sequence`, `channel`, `requested_customers`, `n_customers`, `cost`, а также
`request` и публичные поля `observation`. После обновления оценки добавляется
новое событие `pilot_estimate_updated` с `{sequence, posterior}`; старое событие
не меняется. `fallback_used` сообщает о переходе от OpenAI к расчётным гипотезам.
Помимо событий движка сохраняются `queued`, `running`, `cancel_requested`,
`campaign_result`, `result_ready`, `completed`, `failed`, `cancelled`.
Событие движка `run_completed` означает, что портфель сформирован; окончание
веб-запуска определяется только `Run.status`, после сохранения и проверки результатов.

Frontend хранит ключ запуска по run ID в sessionStorage, блокирует повторный клик
во время POST и не повторяет POST автоматически после сетевой ошибки. Состояние
и события обновляются раз в две секунды, пока расчёт выполняется; страницы событий
обрабатываются по `next_after`, строки дедуплицируются по ID. После конечного статуса
клиент дочитывает события и получает результат. При сетевой ошибке показанные данные
сохраняются, активные расчёты продолжают опрашиваться, также доступен ручной повтор. CSV загружается с текущей сессией.


### Проверенная локальная среда и наборы CSV

Альтернативная factory `apps.campaigns.services.public_environment.local_simulation`
загружает публичный код симулятора из `PARTICIPANT_KIT_DIR` после проверки SHA-256.
Данные берутся из каталога сохранённого dataset; Python-код из загруженных через
интерфейс файлов не исполняется. Для этой factory `run_execution` дополнительно
проверяет наличие и целостность установленного кода. Обе встроенные среды возвращают
`meta.environment.mode=local_simulation`; прогноз не является результатом судейства.

`Run.execution_blocker` содержит причину недоступности расчёта для конкретного
набора либо `null`. Четыре сырых CSV не содержат `customer_profile.csv` и не могут
запускаться в обеих встроенных средах. Черновик и просмотр доступны; новый старт
возвращает `engine_unavailable`, не публикуя задачу. Старые планы сохраняют собственный
dataset, а повтор принятого старта с прежним ключом возвращает сохранённое состояние.
