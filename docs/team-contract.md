# Живая AI-команда: целевой контракт v1

**Статус: согласованное ТЗ для реализации, не перечень уже работающих API.**
Текущие маршруты и поля описаны в [api-contract.md](api-contract.md).
Основа — `b2e5bb3`; план и владельцы — [00-team-plan.md](developers/00-team-plan.md).
Backend обновляет действующий API-контракт/OpenAPI по мере реализации.

## 1. Роли и события

Роли: `lead` (руководитель), `analyst`, `experiment`, `finance`, `control`.
Роль обозначает настоящую функцию движка с входом и результатом. Расчёты и проверки
могут быть детерминированными; число персонажей не задаёт число вызовов LLM.

Сохранить формат движка `{sequence, type, data}` и HTTP-событий
`{id, kind, payload, created_at}`. Новые типы: `task_started`, `task_completed`,
`task_failed`, `task_handoff`. В `data` / `payload` новых событий:

| Поле | Правило |
| --- | --- |
| `task_id` | Строка, постоянная в пределах запуска |
| `actor_id` | Одна из пяти ролей; исполнитель/отправитель события |
| `status` | `running`, `completed` или `failed` для событий задачи |
| `title` | Короткое фактическое описание действия |
| `artifact_ids` | Список ID сохранённых результатов, может быть пустым |
| `evidence_ids` | Список ID наблюдений/артефактов-оснований, может быть пустым |
| `from_actor`, `to_actor`, `to_task_id` | Обязательны для `task_handoff`; фактическая зависимость следующей задачи |

Артефакт: `{id, task_id, type, title, data, evidence_ids}`. Типы:
`hypotheses`, `pilot_observation`, `portfolio`, `explanation`, `comparison`, `validation`.
JSON-данные типизированы по виду артефакта, версия snapshot — `schema_version=1`.
Для передачи новых артефактов observer получает дополнительный массив `artifacts`
в `data` события; backend сохраняет его объекты и публикует ссылки `artifact_ids`.
Ссылки относятся к тому же запуску; backend сохраняет артефакт до публикации события.
Артефакты после сохранения неизменяемы: пересчёт создаёт новый ID.

Старые события и курсор `after` сохраняются. `pilot_completed` записывается один раз;
дополнительная оценка — существующий `pilot_estimate_updated`. Дедупликация происходит
по ID. `run_completed` движка не заменяет окончательный `Run.status` backend.
Анимация может ускорять показ накопленных событий; её завершение не запускает бизнес-действие.

## 2. Snapshot и восстановление

Планируемый `GET /api/v1/runs/{id}/team/`:

```json
{"schema_version": 1, "run_id": "UUID", "snapshot_id": "opaque-id", "last_event_id": 0,
 "tasks": [], "artifacts": [], "available_commands": []}
```

Это только пример формы. Задача содержит `id`, `actor_id`, `status`, `title`,
`artifact_ids`, `evidence_ids`; статусы snapshot: `pending`, `running`, `completed`,
`failed`, `cancelled`. `available_commands` содержит доступные в этом состоянии
типы команд из раздела 3. Snapshot и `last_event_id` должны быть согласованы: события
до курсора уже отражены в snapshot. Затем frontend запрашивает события `after=last_event_id`.
Повторное открытие экрана восстанавливает состояние без нового расчёта.

Внутренний неизменяемый snapshot включает версию движка/датасета, параметры запуска,
подтверждённые наблюдения и затраченные ресурсы, данные для воспроизводимого пересчёта.
Публичная проекция не содержит ключей, путей сервера, приватных эффектов или traceback.

## 3. Команды пользователя

Планируемые маршруты (session/CSRF как у действующего API):

- `POST /api/v1/runs/{id}/commands/` с `Idempotency-Key`.
- `GET /api/v1/runs/{id}/commands/{command_id}/` для результата команды.

Тело POST: `{type, snapshot_id, parameters}`. Backend проверяет версию и параметры.
Первичный ответ — 202 с `{id, type, status, result, error}`; `status`:
`queued`, `running`, `completed`, `failed`; до готовности `result=null`.
Повтор того же тела с тем же ключом возвращает ту же команду; другой запрос с этим
ключом — 409. Ошибки используют текущий формат `{code, message, fields}` внутри `error`.

| `type` | Параметры | Результат и действие |
| --- | --- | --- |
| `explain` | `campaign_id` | Артефакт объяснения с `evidence_ids`; основан на сохранённых фактах |
| `compare` | `constraints: {budget?, allowed_channels?}` | Артефакт сравнения исходного и альтернативного прогнозов на том же snapshot |
| `create_plan` | `name`, `constraints: {budget?, allowed_channels?}` | `{run_id}` нового связанного черновика; расчёт запускается существующим `start/` |

`campaign_id` — ID выбранной кампании/кандидата внутри snapshot; соответствие финальным
рангам задаёт AI. Для ещё не сформированной кампании explain недоступен.
`budget` — decimal-строка в `(0, 100000]`; `allowed_channels` — непустой список допустимых
каналов кейса. Неизвестные поля отклоняются. Остальные настройки новый план наследует
от исходного; ограничения должны быть сохранены backend и переданы в общий движок.

Explain/compare не вызывают `run_pilot` и не меняют исходный запуск. Сравнение учитывает
уже потраченные пилотные ресурсы; невыполнимое ограничение возвращает явную ошибку.
Результат сравнения — прогноз, не новый измеренный результат симулятора.
Новый план получает собственный ID, свежую среду и отдельные лимиты; прошлые пилоты
не копируются в неё как бесплатные наблюдения. Связь с исходным запуском сохраняется.
Свободный текст может предлагать типизированную команду; исполнение проходит те же проверки.

## 4. Интерфейс и границы v1

Визуальная основа — уже опубликованные мини-офис, спрайты и движение по экрану.
Отображение ролей: Бек → `lead`, Дана → `analyst`/`finance` с подписью текущей роли,
Айя → `experiment`, Жан → `control`. Сохранить четыре персонажа и существующий дизайн.

Один источник состояния для «Рабочего стола» и «Живой команды». Каждое действие доступно
обычной кнопкой. Показать затраты пилотов, плановые затраты, лимиты контактов, пилоты,
прогноз, измеренный результат при наличии и предупреждения. Неизвестное — `null`.
Время анимации не блокирует worker. Её пауза/скрытие не являются отменой расчёта.
Управление действующим запуском — существующая отмена; изменения ограничений идут
через новый черновик. Resume и ручные дополнительные пилоты вне текущего worker
не входят в v1. Судейский `Agent.act` работает самостоятельно без ожидания пользователя.
