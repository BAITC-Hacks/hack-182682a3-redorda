# Данные и модели backend

## Импорт пакета участника

```bash
.venv/bin/python backend/manage.py import_participant_data --path data/participant-kit
```

Команда проверяет семь публичных CSV: `customer_profile.csv`, `tariff_dictionary.csv`, `feature_dictionary.csv`, `data/dict_tariff.csv`, `data/traffic.csv`, `data/arpu_monthly.csv`, `data/change_tariff.csv`. Проверяются наличие и обязательные заголовки, повторяющиеся заголовки и ключи справочников, структура каждой строки, конечные числовые значения, допустимые сегменты, уникальность `ID_NUMBER` в текущем профиле и ссылки на известные тарифы. Пустые исторические таблицы отклоняются. В исторических CSV допустимы клиенты вне текущего профиля и отрицательные изменения ARPU; пустой `tariff_plan_code` в истории допустим, поскольку такой пропуск есть в официальном пакете.

В `customer_profile.csv` пустой текущий тариф учитывается в `missing_current_tariff`. Пустые `arpu_segment`, `data_segment` и `call_segment` попадают в соответствующую сводку как `UNKNOWN`. Это значение означает отсутствие данных и **не является допустимым фильтром кампании**. Пустые числовые поля профиля и истории сохраняются как пропуски в исходных CSV; команда не подставляет значения и не копирует персональные строки в БД. `predicted_arpu` обязателен, конечен и неотрицателен.

Проверка всего пакета завершается до записи в БД. Запись выполняется в транзакции через уникальный `Dataset.checksum`, рассчитанный по содержимому семи CSV и их именам. Повторный импорт того же пакета возвращает существующий `Dataset`, не меняет его ID, сводку и связанные запуски. Изменённый пакет получает новый checksum и новую запись. Данные файлов организаторов не меняются. Предварительная проверка ZIP и его SHA-256 выполняется отдельно через `scripts/import_participant_kit.py`.

## Хранилище расчёта

- `Dataset` — сводка проверенного пакета; существующие поля сохранены. `summary` содержит агрегаты из CSV, а не результат кампаний.
- `CampaignRun` — конфигурация запуска и статус `draft`, `queued`, `running`, `completed`, `failed` или `cancelled`. Существующие поля сохранены. `task_id` хранит ID фоновой задачи; `cancel_requested` — запрос остановки; `started_at` и `finished_at` — фактическое время; `error_code` и `error_message` — сведения о сбое. Новые поля имеют безопасные значения по умолчанию для ранее созданных запусков.
- `RunEvent` — журнал прогресса. `id` — возрастающий BigAutoField для чтения событий после заданного ID; `kind` и `payload` описывают событие; `created_at` — время записи. Связь: `run.events`.
- `Pilot` — пилот с номером `sequence`, исходными `request` и `response`, числом клиентов `n_customers`, денежной стоимостью `cost` (`Decimal(12, 2)`) и временем создания. Пара `(run, sequence)` уникальна. Связь: `run.pilots`.
- `CampaignResult` — финальная кампания с порядком `rank`, конкурсными полями в `campaign`, фактическими/расчётными значениями в `metrics` и текстом `explanation`. Пара `(run, rank)` уникальна. Связь: `run.campaign_results`.
- `RunResult` — одна общая сводка `summary` на запуск, с временем создания. Связь: `run.result`.

JSON-поля не заполняются предполагаемыми результатами. Сервис расчёта должен записывать туда только полученные значения. Денежные значения внутри JSON следует сериализовать десятичными строками; отдельное денежное поле `Pilot.cost` хранится в БД как `Decimal`. Модели не запускают Celery и не вычисляют эффект сами.

## Проверки

```bash
make check
.venv/bin/python backend/manage.py migrate
.venv/bin/python backend/manage.py import_participant_data --path data/participant-kit
```

Миграция `0002` добавляет поля и таблицы без удаления старых данных. Тест миграции создаёт `Dataset` и `CampaignRun` на схеме `0001`, затем проверяет их после перехода на `0002`.
