# Живая AI-команда: параллельная работа троих

**Точка старта:** `main` на `b2e5bb3` (23 сентября 2026). Перед началом взять
последний `origin/main` вместе с этим планом. Движок, его backend-адаптер,
авторизация, start/cancel/events/results/CSV и четыре пиксельных персонажа уже в коде.
Персонажи пока показывают сценарии по таймеру. Готовность production проверяется отдельно.

**Цель:** один реальный маркетинговый запуск доступен через обычные таблицы и
живую команду. Пользователь открывает задачу персонажа, видит основания решения,
запрашивает объяснение/сравнение, создаёт изменённый план и скачивает CSV.

## Все начинают параллельно

| Разработчик | Ветка | Зона и первый независимый шаг |
| --- | --- | --- |
| [1. Backend](01-backend.md) | `codex/team-backend` | `backend/`, инфраструктура, HTTP-контракт/OpenAPI; хранение задач, результатов команд и восстановление состояния |
| [2. AI](02-agent.md) | `codex/team-engine` | `packages/campaign_engine/`, `agent.py`, скрипты движка; роли, артефакты и explain/compare поверх сохранённых данных |
| [3. Frontend](03-frontend.md) | `codex/team-frontend` | `frontend/`; общее состояние запуска, два режима и анимации по событиям |

Работать в отдельных worktree, созданных от актуального `origin/main`. Пример
для backend из основного checkout (для остальных заменить имя ветки и каталога):

```bash
git fetch origin
git worktree add ../redorda-team-backend -b codex/team-backend origin/main
```

Если ветка/worktree уже существует, продолжить в нём; не сбрасывать чужие изменения.
Не ждать завершения другой ветки: использовать [целевой контракт v1](../team-contract.md).
Синтетические контрактные примеры допустимы в тестах; пользовательские показатели
и анимации успешной работы должны опираться на реальные сохранённые события.

## Общая договорённость

- HTTP и OpenAPI ведёт разработчик 1; типы и observer движка — разработчик 2;
  TypeScript-типы и клиент — разработчик 3. Изменение стыка согласовать с потребителями.
- Идентификаторы ролей: `lead`, `analyst`, `experiment`, `finance`, `control`.
- Общие сценарии v1: `explain`, `compare`, `create_plan`; запуск/отмена/экспорт уже есть.
  Explain/compare используют сохранённый snapshot и не проводят пилоты.
- Новые ограничения запускаются через связанный новый черновик и явный `start/`.
  Текущая среда не поддерживает resume. Скрытие/пауза анимации меняют только отображение.
- Один `run_id`, журнал событий, бюджет и результаты для обоих режимов. Переключение
  и перезагрузка не создают задачу Celery и не повторяют пилот.
- Разделять фактические расходы, плановые расходы, прогноз и измеренный результат.
  В текущем web-пайплайне `simulator_result=null`; отсутствующий показатель остаётся `null`.
- Сохранять общую стратегию для web и `Agent.act`; судейский запуск полностью автоматический.

## Объединение и приёмка

Разработка параллельная. Разработчик 1 отвечает за сборку: AI → backend → frontend;
это порядок интеграции, а не очередь начала работы. Общие контракты публиковать раньше
завершения всех функций. Перед merge обновить ветки из `origin/main`, сохранить чужую
работу; использовать обычные merge и push без force push.

Готово, когда реальный запуск проходит до CSV, задачи и передачи содержат доказательства,
объяснение/сравнение не расходуют ресурсы, новый план имеет отдельный ID, а переключение
режима и повтор запросов не меняют результаты и не повторяют платные действия.

Общие проверки: `make check`, `make schema`; PostgreSQL-проверки конкурентного запуска,
браузерный сценарий двух режимов и 10 seed оценки движка. В отчёте указать реально
выполненные команды, результаты и оставшиеся ограничения. Не коммитить ключи или данные.
