# Разработчик 1 — Backend команды агентов

**Ветка:** `codex/team-backend`. **Зона:** `backend/`, инфраструктура, API/OpenAPI и общая интеграция.
Django 5.2, PostgreSQL, Redis, Celery. Общий план: [00-team-plan.md](00-team-plan.md).
Действующий API: [api-contract.md](../api-contract.md); планируемое расширение: [team-contract.md](../team-contract.md).

## Текущая точка

В `main` (`b2e5bb3`) уже подключены общий runner, factory публичной среды, observer,
история датасета, прогнозы, отмена, события и CSV. Frontend реализует авторизацию и запуск.
Следующие этапы расширяют существующий сценарий; стратегия остаётся в `campaign_engine`.

## Этап 1 — задачи, передачи и результаты

- Согласовать с AI/frontend планируемый контракт; сохранять задачи, исполнителей, передачи и артефакты с идентификаторами и ссылками на подтверждающие события.
- Расширить текущие события без нарушения существующего polling. Передача возникает при реальном переходе работы; анимация не управляет выполнением.
- Добавить snapshot команды с курсором событий для восстановления экрана после перезагрузки без пропусков и повторных действий.
- Разделять фактические расходы пилотов, плановые расходы кампаний, прогноз и результат оценщика. Неизвестные значения — `null`.

## Этап 2 — команды пользователя

- Реализовать типизированные `explain`, `compare`, `create_plan` по общему контракту: валидация, сессия/CSRF, сохранённые статус и результат команды.
- `explain` и `compare` вызывают функции AI-разработчика по сохранённым данным и возвращают проверяемые материалы; новые пилоты не запускаются.
- `create_plan` создаёт связанный черновик с новыми ограничениями; расходы исходного запуска сохраняются, новый расчёт требует отдельного запуска.
- Для команд использовать `Idempotency-Key`: повтор возвращает ту же команду; тот же ключ с другим содержимым — конфликт. Платные действия не дублируются.
- Доступные действия возвращает сервер. Pause/resume, ручной дополнительный пилот и изменение работающей среды не включать без согласованной поддержки движка.

## Этап 3 — интеграция и сдача

- Подключить оба режима frontend к одному запуску, snapshot, командам и журналу; состояние восстанавливается после переключения и переподключения.
- Проверить полный сценарий, повторные команды, отмену, сбой Redis/worker и ошибку LLM. Не повторять весь runner автоматически после оплаченного пилота.
- Обновить API-контракт и OpenAPI, передать схему frontend для генерации типов. Выполнить `make check`, `make schema`; конкуренцию проверить на PostgreSQL.
- Зафиксировать выполненные проверки и ограничения; отсутствие измеренного результата оценщика явно сохраняется в API.

**Готово:** реальные задачи и материалы доступны через обычный интерфейс и персонажей; повтор запроса не повторяет действие; итоговый CSV соответствует сохранённому плану.

**Инструкция ИИ:** сначала прочитай `AGENTS.md`, общий план и оба контракта; работай в отдельном worktree указанной ветки. Не переписывай стратегию, не меняй frontend и скрытый оценщик. Общие изменения интегрируй обычным merge после проверок; не публикуй секреты и локальные данные.
